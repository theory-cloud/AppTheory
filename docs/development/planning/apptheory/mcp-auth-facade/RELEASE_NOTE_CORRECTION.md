# Release-note correction mechanism (M0, item 8)

Status: mechanism spec for review (M0). No release notes or CHANGELOG are edited in M0.
Last updated: 2026-10-12
Owner: AppTheory

G11: the 6.0.0 `CHANGELOG.md` omits the M2 MCP transport-authorizer change from its `⚠ BREAKING CHANGES`
list, even though `UPGRADING.md` documents it. The change shipped as
`fix(security): M2 MCP facade authentication and task runtime hardening (Go/TS/Py/CDK)` (#1124) at commit
`b3ef924`; it is absent from the BREAKING CHANGES list at `CHANGELOG.md:6-12` while the entry appears in
"Bug Fixes" at `CHANGELOG.md:62`. This document names **how** the generated release notes are corrected given
Release Please ownership. It does not perform the correction (M0 non-goal: no CHANGELOG edits).

## Ownership facts (grounded)

- Release Please owns `CHANGELOG.md` and the draft GitHub Release bodies. `release-please-config.json` sets
  `release-type: go`, `draft: true`, `include-v-in-tag: true`, and does **not** override `changelog-path`, so
  the default `CHANGELOG.md` is the generated file. The `release-pr.yml` workflow watches `CHANGELOG.md` as a
  generated output.
- Release Please **never regenerates a past release section**: a new release appends a new section built from
  commits *since the last release tag*. The 6.0.0 section is therefore frozen at the shape it had when 6.0.0
  was cut.
- `docs/release-process.md` states the division of ownership explicitly: "The changelog lists commits;
  `UPGRADING.md` lists consumer action and per-line compatibility notes." `UPGRADING.md` is **not** a
  generated file.
- Operator ruling: the v6.0.0 **tag and assets are immutable**, so the released artifacts are not rewritten.

## Mechanism

The correction has three parts, in this order.

### 1. The authoritative consumer-action note lives in `UPGRADING.md` (already true) and is made discoverable

`UPGRADING.md` already has the "MCP transport routes require credentials by default" section. Add (in M4, a
`docs:` change) a discoverability entry so the omission is findable from the release process: a short
"Release-note corrections" section in `docs/release-process.md` (or a small
`docs/release-notes-corrections.md` linked from it) recording:

- which release note is incomplete (6.0.0 `⚠ BREAKING CHANGES`),
- the omitted entry (the M2 MCP transport-authorizer default flip, commit `b3ef924`, PR #1124),
- the consumer action (read the `UPGRADING.md` section; configure `transportAuthorizer` or the explicit
  opt-out).

This is the durable, release-please-resistant home for the correction. It cannot be lost by a later generated
release because Release Please does not own it.

### 2. The next generated release carries a visible correction entry

Put the correction into the **next** release section (6.1.0), release-please-natively, by landing the
correcting change as a Conventional Commit that release-please renders into the new changelog section. The
correcting commit's body names the omission and links the `UPGRADING.md` section, for example:

```
fix(docs): note the omitted 6.0.0 BREAKING CHANGES entry for MCP transport auth

The 6.0.0 BREAKING CHANGES list omitted the M2 MCP transport-authorizer default
flip (commit b3ef924, PR #1124). UPGRADING.md documents the change; the changelog
did not. This entry records the correction for the release notes.

Refs b3ef924
```

Because the corrected release is the carrier of this program's changes anyway, the correction rides the same
release train and appears in its generated notes. The commit is typed so it is release-eligible; a pure
`docs:` type would not appear in the generated section, which is why the correction is deliberately
release-visible.

### 3. The immutable 6.0.0 GitHub Release body is an operator decision, not a steward edit

The GitHub Release body for the published 6.0.0 tag is **not** regenerated by Release Please after publish.
Editing it is possible (it is a GitHub Release body, not a git object) but it is outside Release Please
ownership and outside M0's write scope (no GitHub API mutation). Recommended: the operator edits the 6.0.0
Release body once to add the omitted breaking-change bullet, or explicitly declines and relies on parts 1–2.
This is recorded as an open decision below.

## What is explicitly forbidden

- **Do not hand-edit the generated `CHANGELOG.md` 6.0.0 section** in a normal PR. Release Please owns the file;
  a later generated release PR rebuilds it from commit history and would drop or duplicate the hand edit, and
  the repo's release-train rules already forbid ad-hoc release-machinery edits.
- **Do not rewrite the released 6.0.0 tag or its assets** (operator ruling: immutable).
- **Do not land the correction as a release-triggering `feat:`/`fix:` in M0**; M0 is `docs:`-typed and must not
  trigger a release. The correction commit belongs to M4, on the release train, deliberately.

## Verification

- The correction is a documentation change; `make test`'s `scripts/verify-version-alignment.sh` and the
  release gates are unaffected.
- After the correcting release publishes, confirm the generated section contains the correction entry and that
  `UPGRADING.md` is linked; confirm the 6.0.0 section was not touched by automation.

## Open decisions

1. Whether the operator edits the immutable 6.0.0 GitHub Release body (recommend: yes, one-time, by the
   operator; or explicitly decline).
2. Whether the durable correction record is a section in `docs/release-process.md` or a dedicated
   `docs/release-notes-corrections.md` (recommend: dedicated file, linked from the release process, so future
   corrections accumulate in one auditable place).
